# Kodo: архитектура многоагентной разработки через разделение контекста LLM

LLM-ассистенты эффективны в решении локальных задач, однако при работе над сложными многоэтапными проблемами их производительность снижается. Это связано с принципом работы самих LLM: их механизм внимания и процесс генерации сильно привязаны к предыдущему контексту. Модель, написавшая фрагмент кода, склонна повторять и развивать собственные логические ошибки, поскольку они являются следствием её предыдущих рассуждений. Её контекстное окно "загрязнено" историей реализации.

В классической разработке эта проблема решается через код-ревью — процесс, в котором независимый инженер, не имеющий предвзятости автора, анализирует изменения. Опенсорсный оркестратор [kodo](https://github.com/ikamensh/kodo) применяет этот же принцип к LLM-агентам, используя архитектуру принудительного разделения контекстов.

## Архитектура и специализация агентов

Основа kodo — это pipeline, в котором агенты-LLM выполняют строго определенные роли. Ключевым элементом является информационная изоляция агента-ревьюера от агента-исполнителя.

*   **Orchestrator**: Управляющий агент (например, Gemini Flash), работающий на уровне мета-задач. Декомпозирует цель, формирует план, распределяет задачи между исполнителями. Не пишет код.
*   **Worker**: Агент-исполнитель (например, Claude Code). Получает конкретную техническую задачу и пишет код для её решения. Работает в полном контексте истории задачи.
*   **Architect**: Агент-ревьюер. Получает на вход **только** изначальную высокоуровневую цель и `git diff` с изменениями от Worker'а. У него нет доступа к истории диалога и рассуждениям, которые привели к созданию этого кода.
*   **Tester**: Выполняет тесты для верификации функциональности.

Цикл разработки представляет собой последовательность изолированных API-вызовов: Worker реализует задачу. Architect проверяет `diff`. Если найдены проблемы, код возвращается на доработку с конкретными замечаниями. Если `diff` принят, изменения коммитятся.

## Техническое обоснование разделения контекста

Эффективность этой архитектуры объясняется тем, как работают LLM.

Контекст **Worker'а** при очередном вызове API концептуально выглядит так:
```json
{
  "model": "claude-3-5-sonnet",
  "messages": [
    { "role": "user", "content": "[Изначальная цель]..." },
    { "role": "assistant", "content": "[Рассуждения Orchestrator'а]..." },
    { "role": "user", "content": "[Задача от Orchestrator'а]..." },
    { "role": "assistant", "content": "[Предыдущие попытки реализации кода]..." },
    { "role": "user", "content": "[Отчет об ошибке от Tester'а]..." },
    { "role": "assistant", "content": "[Текущая реализация кода]..." }
  ]
}
```
Логика генерации (Chain-of-Thought) сильно зависит от истории реализации. Механизм внимания модели сфокусирован на токенах, которые она сама сгенерировала, что создает сильную предвзятость и мешает увидеть структурные недостатки.

Контекст **Architect'а** намеренно минималистичен и не содержит истории:
```json
{
  "model": "claude-3-5-sonnet",
  "messages": [
    { "role": "user", "content": "[Изначальная цель] + [Код в виде git diff]..." }
  ]
}
```
Это полностью отдельный, изолированный API-вызов. LLM не имеет доступа к рассуждениям Worker'а. Это заставляет модель начать новый, "чистый" Chain-of-Thought, анализируя код исключительно на основе его соответствия первоначальной цели. Такой подход позволяет выявлять проблемы, которые принципиально невидимы для агента, находящегося внутри процесса реализации.

## Практический пример: оптимизация

Рассмотрим реальный пример из логов kodo, где была поставлена мета-задача: «оптимизируй собственный основной цикл для повышения производительности».

### Итерация 1: Утечка ресурсов

Worker, стремясь к параллелизму, внедрил `multiprocessing.ProcessPool`.
*   **Architect REJECTED**: `diff` отклонен. Комментарий: "Пул процессов (`ProcessPool`) создается, но никогда не закрывается. Это приведет к утечке ресурсов."

Worker был сфокусирован на задаче распараллеливания, но упустил деталь жизненного цикла ресурса. Architect, анализируя `diff` в изоляции и не зная о предыдущих шагах, увидел создание объекта, но не увидел его корректного уничтожения.

### Итерация 2: Загрязнение состояния

Worker добавил код для закрытия пула, исправив утечку. Тесты проходили.
*   **Architect REJECTED**: `diff` снова отклонен. Комментарий: "Обнаружено **загрязнение состояния через переменные класса между запусками** (class-variable contamination between runs)."

Это наиболее важный этап. Worker, последовательно исправляя предыдущие ошибки, продолжал действовать в рамках своей первоначальной архитектуры. Для него код выглядел как логичное исправление. Однако Architect, каждый раз выполняя бесконтекстный анализ `diff`, выявил более глубокую архитектурную проблему: состояние, хранившееся в переменных класса, могло персистировать между независимыми запусками, вызывая непредсказуемые побочные эффекты. Worker был слеп к этой проблеме, так как она была логическим продолжением его собственного Chain-of-Thought. Architect же, благодаря изолированному API-вызову, смог обнаружить этот нетривиальный дефект.

Без агента-ревьюера, работающего в отдельном контексте, обе эти ошибки попали бы в кодовую базу.

## Конфигурация и использование

Настройка проекта производится в директории `.kodo/`:

*   `config.json`: Глобальные настройки.
*   `team.json`: Описание ролей, моделей и системных промптов для агентов.

Запуск задачи в фоновом режиме:
```bash
# Использовать цель из файла feature.md, установить лимит в 10 циклов
kodo --goal-file feature.md --cycles 10 -y ./my-project
```
Kodo интегрирован с Git, создавая коммиты после каждого успешно завершенного и утвержденного Architect'ом этапа.

## Ограничения

*   **Требования к постановке цели.** Система требует четко сформулированной технической задачи с измеримым результатом (например, «реализовать аутентификацию по OAuth 2.0» или «рефакторить модуль X для соответствия Y»). Она не предназначена для абстрактных исследовательских (R&D) задач вроде «придумай, как улучшить онбординг».
*   **Зависимость от LLM.** Качество результата напрямую зависит от возможностей используемых моделей. Роль Architect'а требует мощной модели для нахождения нетривиальных ошибок.
*   **Риск зацикливания.** В редких случаях Worker и Architect могут войти в бесконечный цикл правок. Например, Worker реализует решение, а Architect его отвергает, но Worker не понимает мотивов критики и предлагает аналогичное решение. Это требует ручного вмешательства для корректировки цели или кода.
*   **Состояние кодовой базы.** Наилучшие результаты достигаются на проектах с существующей архитектурой, тестами и линтерами, которые служат дополнительными ориентирами для агентов.

## Вывод

Kodo — это не новая LLM, а архитектурный паттерн для управления существующими моделями. Его ценность заключается в pipeline, который принудительно разделяет контексты реализации и ревью через изолированные API-вызовы. Это позволяет обойти врожденную предвзятость LLM к собственному сгенерированному коду и отлавливать класс ошибок, которые в ином случае остались бы незамеченными.

Такой подход позволяет делегировать системе сложные, многоэтапные задачи, получая на выходе не просто сгенерированный код, а набор атомарных, прошедших независимую проверку коммитов.
